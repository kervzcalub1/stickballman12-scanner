## The idea (in the user's words)

> A supplier (e.g. "Joey in Texas") **scans the shoes he's shipping out**, and that
> builds a **purchase order** on his side. We **assign him an order number** (e.g.
> `54321`). When the box arrives, our warehouse **scans it in against that same PO**.
> The system **compares what he said he shipped vs. what we actually received** and
> **flags any shortage, overage, wrong size, or wrong SKU** so we can go back to him
> ("Joey, your PO is missing 3 shoes"). Once fully received, the stock becomes
> available in our inventory.

The point is **inbound receiving starts before the product arrives**, and every
shipment is **reconcilable** end to end.

## Clarified workflow — 2026-07-09 diagram

The user supplied a flow diagram refining the **front half** (order creation → supplier
scan-out → ship → track). Two sides share one **System Database**.

### A) PH Team creates the batch/PO shell — *before* the supplier scans
- **PH Team** fills a **Form (Batch)** → "Send to the system".
- The form captures: **Supplier Name**, **Tracking Number/s**, **Tag/Code Name +
  Date of Purchase**.
- These persist to the **System Database**. PH Team can **Track the batch** from their side.

### B) Supplier logs in and scans the contents against it
- Suppliers get a **login system** — ideally a subdomain **`supplier.stickballman12.com`**.
  *(This confirms Option A below.)*
- Supplier **retrieves their tracking number(s) / order from the system**
  ("Retrieve from the system") — they do **not** create the order.
- Supplier **Add/Scan shoe details (SKUs and Qty)** against that tracking number →
  persists to the System Database.
- **Manpower** drops the box **to the courier**.
- **Track shipment status** — via **courier API if possible, otherwise a third-party
  tracking service**. Status flows back to the System Database → the batch is trackable
  end to end.

### What changed vs. the original spec (below)
1. **Initiation flips to the PH Team.** The supplier no longer *creates* the PO — the PH
   team creates the shell (supplier + tracking + tag/date) and the supplier *retrieves* it
   and fills in **SKU/Qty** by scanning. (So in the data model, a PO/batch shell can be
   created empty by PH and populated by the supplier.)
2. **Tracking number(s) are entered up front by PH** and retrieved by the supplier, rather
   than generated by the supplier at ship time.
3. **Courier + shipment tracking is now explicit** — a new integration leg (courier API or
   a third-party aggregator) tracks the box in transit and feeds status back.
4. **Option A confirmed** — supplier login via subdomain.

### Back half — reconciliation ✅ still in scope
Confirmed 2026-07-09: the warehouse **scan-in + reconciliation** (shortage / overage /
wrong SKU / wrong size) **stays** — the diagram just omitted it. This remains the **full
loop**: PH shell → supplier scan-out → ship → courier tracking → **warehouse receives
against the PO** → reconcile. The reconciliation design (below) applies unchanged once the
box arrives.

### Tracking number ✅ decided: one courier number, PH-assigned
Confirmed 2026-07-09: the "Tracking Number/s" PH enters up front **is the real courier
tracking number**. The supplier **ships under it** (read-only retrieval), and the courier
API polls **that same number** for shipment status. → **one** `tracking_number` field (per
box for multi-box), no separate internal-vs-courier split. The **Tag/Code Name** is a
distinct internal label (with **Date of Purchase**), not a second tracking number.

### The "Batch" = one form, many shipping labels ✅ (2026-07-09)
The **Form *is* the Batch**, and a batch can span **multiple shipping labels / tracking
numbers** (one physical box per label) — the direct outbound mirror of our existing
**multi-box receiving** (`batch_boxes`).
- At creation, **ask PH how many labels** are in the batch; PH enters **one (pre-assigned,
  real courier) tracking number per label**.
- The supplier picks up the **pending batch** and — **out of the system, via the group
  chat** — matches the physical labels PH messaged them against the batch's tracking
  numbers. *This matching is deliberately manual (comms only); we do NOT build it.*
- The supplier then **adds items under each tracking number** (per-label item scanning,
  identical UX to multi-box receiving).
- The **batch closes only when every tracking number has been shipped.**
- **Data-model impact:** `po_boxes` (one row per label: `box_number`, `tracking_number`,
  per-label `status`) is now **core, not optional**. Batch/PO flips to `shipped` only once
  **all** labels are shipped; per-label status drives the "X of N shipped" progress.

### Shipment-tracking API ✅ recommended: 17TRACK (aggregator, not a single courier)
PH enters raw tracking numbers from **potentially different couriers** (test data showed a
UPS `1Z…`), so use a **multi-carrier aggregator with carrier auto-detection + webhooks** —
never a single courier's API. We hand it a number; it detects the carrier and **pushes
status back** to a webhook, which we write onto the label. Per label store `carrier`
(auto-detected), `tracking_status`, `last_checkpoint`, `checked_at`.

| Service | Carriers | API access | ~Cost | Verdict |
|---|---|---|---|---|
| **17TRACK** ✅ | 2,500+ (strong intl / China) | **on free + cheap plans** | Free 140/mo · packs ~**$0.017**/tracking (7k/$119) | **Pick for v1** — API isn't paywalled, cheap to scale, webhooks. |
| AfterShip | 1,300+ | **Premium only** | **$70/mo** min for API (500 shp, then $0.12) | Most polished/mature; API gated high — revisit at large volume. |
| EasyPost / Shippo | 100+ (US-centric) | yes | pay-per-tracker | Only if we later want to **buy labels** too, not just track. |

**Recommendation: 17TRACK for v1** — free tier to build/test, webhook-driven (no polling
infra), broad coverage for overseas suppliers, and API access without a $70/mo floor.
Keep the integration behind a thin adapter so swapping to AfterShip later is a one-file
change. *(Verify current pricing/limits at signup — tiers move.)*

### Decisions resolved — **Phase 0 is unblocked** (2026-07-09)

**Storage: dedicated `purchase_orders` (+ `po_boxes` + `po_lines`), NOT a reused `batch`.**
The PO holds the **expected** side (what the supplier scanned out); a normal receiving
`batch` holds the **actual** side (what the warehouse scanned in), linked via
`batches.po_id`. Reasons this beats reusing one batch record:
- Reconciliation needs **two independent quantity sets** (expected vs. actual). One record
  would have to carry both — messy and error-prone.
- **Supplier scan-out must NOT mint VINs or create inventory.** The receiving `commit`
  pipeline mints VINs + inserts `items`; running the supplier through it would create
  phantom stock before the box exists. A separate PO write path avoids that entirely.
- We still **reuse the UI** (the Add-Item scanning modal, product lookup, per-size
  increment) and the **multi-box pattern** (`po_boxes` mirrors `batch_boxes`) — reuse where
  it's safe, separation where it matters.

**Creator: the PH Team — confirmed, and they make the labels.** PH **creates/buys the
shipping labels** for the supplier, which is *why* real courier tracking numbers exist
up front: PH purchases each label (via their own courier account), records its tracking
number on the batch, and sends the label to the supplier **through the group chat**. The
supplier ships under those numbers. *(Forward note: because PH already buys labels, a
label-purchase API like EasyPost/Shippo could later generate the label + number inside the
system — out of scope for v1, which only tracks via 17TRACK.)*

**Courier tracking: 17TRACK** — resolved above.

## Goal / acceptance criteria

1. Supplier scans out product → a PO is created automatically (qty, SKU, size, cost,
   supplier name, tracking/box info when available).
2. Warehouse receives the shipment and scans product in **against that PO**.
3. System matches scan-out vs. scan-in, line by line (SKU + size).
4. Any **shortage / overage / wrong size / wrong SKU** is flagged automatically.
5. When fully received, the units become normal available inventory (existing flow).

## How this fits the current system

Today (see `docs/context/receiving.md`): a warehouse user creates a **batch**
manually *after* the box arrives — supplier + tracking are entered at Step 1, shoes
are scanned in Steps 2–4, and `api/batches/commit.js` mints VINs + inserts `items`.
Multi-box batches already model **`batch_boxes`** (per-box tracking, out-of-order
commit, atomic claim).

This feature **prepends a supplier-side step**: the batch's expected contents now
exist *before* Step 1, as a **purchase order** the supplier built by scanning. The
warehouse batch then **links to that PO** and reconciles against it. Almost all of
the scan-in machinery (scanner gun auto-focus, UPC/SKU auto-detect, per-size
auto-increment, VIN mint, box model) is **reused unchanged** — we add a PO layer in
front and a reconciliation layer on top.

### Key decision — how does the supplier interact? (✅ decided: Option A)

> **Resolved by the 2026-07-09 diagram:** suppliers get a **login system**, ideally the
> subdomain `supplier.stickballman12.com` → **Option A**. Options B/C kept below for record.

The supplier is external and in another state. Three options:

| Option | What it is | Trade-off |
|---|---|---|
| **A. Supplier login (new `supplier` role)** ✅ recommended | Supplier gets an admin-approved account scoped to only their own POs. A stripped-down home: "My Outbound Shipments" + "New shipment (scan out)". Reuses the existing scanner, product lookup, auth. | Cleanest, most true to the voice memo ("he scans what's coming"). Cost: a new role + strict per-supplier scoping on every PO endpoint (same discipline as the `kind='instore'` PH-exclusion). |
| **B. Tokenized magic link (no account)** | We generate a per-shipment link/code; supplier opens a minimal scan page, no login. | Lowest friction for the supplier. Cost: a second, weaker auth path to build + secure; harder to attribute/audit. |
| **C. Warehouse enters the PO** (CSV / paste / we key it) | No supplier app at all; we create the PO from a spreadsheet the supplier sends. | No supplier-facing build. Cost: defeats the "receiving starts before arrival on the supplier's side" goal — it's just early data entry by us. |

**Recommendation: Option A** (new `supplier` role). It matches the vision, reuses the
existing SPA + scanner + auth, and keeps a clean audit trail. The rest of this plan
assumes A, but the data model works for B/C too (a PO can be created by any role).

## Data model (new tables + one FK)

Add to `scripts/db-setup.mjs` (idempotent `CREATE TABLE IF NOT EXISTS` /
`ADD COLUMN IF NOT EXISTS`), and run `db:setup` on **local and prod** (schema-drift
is the #1 trap — `docs/context/deploy.md`).

### `purchase_orders`
```
id              BIGSERIAL PK
po_code         TEXT UNIQUE            -- human order number ("54321" or PO-<seq>)
supplier_name   TEXT NOT NULL         -- matches suppliers.name
supplier_user_id BIGINT               -- who scanned it out (supplier role), nullable
status          TEXT NOT NULL         -- draft | shipped | receiving | reconciled | closed
expected_boxes  INT                   -- optional, mirrors batches.expected_boxes
tracking_number TEXT                  -- overall tracking if single box; else per-box below
notes           TEXT
created_by / created_at
shipped_at                            -- when supplier marks it shipped (locks the PO)
received_batch_id BIGINT              -- FK batches.id, set when warehouse receives
reconciled_at
```
- `po_seq` sequence for auto codes; supplier/admin may override with a typed code word.
- `status` lifecycle: **draft** (supplier still scanning) → **shipped** (supplier
  finalized; lines frozen) → **receiving** (warehouse started scanning in) →
  **reconciled** (fully received + deltas computed) → **closed**.

### `po_lines` — the "what the supplier says he shipped"
```
id            BIGSERIAL PK
po_id         BIGINT FK purchase_orders
sku           TEXT
size          TEXT
name          TEXT                    -- from product lookup at scan time
upc, colorway, gender TEXT
qty_expected  INT NOT NULL DEFAULT 0  -- incremented as the supplier re-scans
unit_cost     NUMERIC
created_at / updated_at
UNIQUE (po_id, sku, size)             -- one line per SKU+size; re-scan increments qty
```
Re-scanning a SKU/size **increments `qty_expected`** — mirrors receiving's
per-size auto-increment so the supplier UX is identical to ours.

### `po_boxes` — **core** (one row per shipping label)
Mirror of `batch_boxes` for the outbound side — **required, not optional** (confirmed
2026-07-09: a batch spans multiple labels). Columns: `id, po_id, box_number,
tracking_number, carrier` (auto-detected), `status` (pending → shipped → in_transit →
delivered), `tracking_status, last_checkpoint, checked_at`. PH creates one row per label at
batch creation (with the tracking number); the supplier scans items under each; the PO
`shipped` only when **all** `po_boxes` are shipped. `po_lines` gain an optional
`po_box_id` so items attach to their label.

### `batches.po_id` — the link
`ALTER TABLE batches ADD COLUMN IF NOT EXISTS po_id BIGINT` → the received batch
points back to its PO. Reconciliation joins `po_lines` (expected) against the
`items` inserted under that batch (actual), grouped by `(sku, size)`.

### Reconciliation — computed, not a fourth table (v1)
No `po_discrepancies` table initially. A **view/query** compares expected vs.
received on demand:
- **expected** = `po_lines` grouped by `(sku, size)`.
- **received** = `items WHERE batch_id = po.received_batch_id` grouped by `(sku, size)`.
- For each key, `delta = received - expected` →
  - `delta < 0` → **shortage**
  - `delta > 0` → **overage**
  - key in received but SKU not in expected → **wrong SKU**
  - SKU expected but this size not expected → **wrong size**
  - `delta == 0` → **match**
- Store a **summary snapshot** on the PO at reconcile time (`reconciled_at` + a
  `reconciliation JSONB` column) so the report is stable after the fact. (Add
  `purchase_orders.reconciliation JSONB` — cheap, avoids a table.)

## API endpoints (Express handlers in `api/**`, served by `server.mjs`)

Follow the house order: `applySecurity` → `requireAuth/Role` → `rateLimit` →
`getJsonBody`. **Every PO endpoint must scope a `supplier` user to their own PO**
(by `supplier_user_id` / `supplier_name`) — the same guard-everywhere discipline as
`kind='instore'`. Warehouse/admin see all.

Supplier-side (create the PO by scanning):
- `POST /api/po/create` — start a draft PO (assigns `po_code`, supplier).
- `POST /api/po/scan` — add/increment a line `{poId, sku|upc, size, cost}`; runs the
  same product lookup as receiving to fill name/colorway/etc.
- `POST /api/po/line` — manual qty edit / remove a size / delete a line.
- `POST /api/po/ship` — finalize: status `draft → shipped`, freeze lines, attach
  tracking/box info.
- `GET  /api/po/list` — supplier: my POs; warehouse/admin: all (filters by status/date).
- `GET  /api/po/get?id=` — full PO + lines.

Warehouse-side (receive against a PO + reconcile):
- `GET  /api/po/open` — POs in `shipped`/`receiving` status, for the receive picker.
- Extend `api/batches/commit.js` + box-commit to accept **`poId`**: set
  `batches.po_id`, flip PO to `receiving` on first commit, and to `reconciled` +
  snapshot on finish.
- `GET  /api/po/reconciliation?poId=` — expected vs. received table + flags.

`db.js` additions: `createPo, addPoScan, updatePoLine, listPos, getPoWithLines,
shipPo, linkBatchToPo, reconcilePo` (+ the usual BIGINT-id-is-a-string coercion —
`Number(row.id)`, per `data-model.md`).

## Reconciliation rules (the flags)

Grouped by `(sku, size)` for one PO ↔ its received batch:

| Condition | Flag |
|---|---|
| received `<` expected | **Shortage** (`-N`) |
| received `>` expected | **Overage** (`+N`) |
| received SKU not on the PO at all | **Wrong SKU** (unexpected) |
| SKU is on the PO but this size wasn't expected | **Wrong size** |
| received `==` expected | Match ✓ |

PO is **fully received** when every expected line has `received ≥ expected` and no
unexpected SKUs remain (or when the warehouse explicitly marks it reconciled with
noted discrepancies). Snapshot the table to `purchase_orders.reconciliation` at that
moment so the report doesn't drift.

## Deployment — the supplier subdomain (`supplier.stickballman12.com`)

**Architecture: one Railway service; the subdomain is a second custom domain — not a
separate deploy.** Both `stickballman12.com` and `supplier.stickballman12.com` hit the
**same** Express app + same DB. The app branches on hostname for the supplier UX; the real
security boundary is the **role-scoped endpoints** (the hostname is convenience/branding,
never authz).

**The current code is already subdomain-ready — no infra code changes:**
- Same-origin CORS (`applySecurity` doesn't echo origins) → nothing to allowlist.
- Host-relative CSP (`connect-src 'self'`) → works on any hostname.
- Host-preserving HTTPS redirect.
- Auth is a **`sessionStorage` Bearer token** (`src/api.js`) → per-origin, so supplier
  logins on the subdomain are naturally isolated from staff logins on the apex.

**Railway:** service → Settings → Networking → Custom Domain → add
`supplier.stickballman12.com`. Railway returns a CNAME target and auto-issues a Let's Encrypt
cert once DNS resolves. No new service, env, or build.
- **Hobby plan cap: 2 custom domains per service** (Pro = 20). The built-in
  `*.up.railway.app` doesn't count. So on Hobby: apex only (1) + `supplier` (2) = fits; but
  apex + `www` (2) already maxes it — do the `www`→apex redirect at Cloudflare (not as a
  Railway domain) to free the slot, or upgrade to Pro. Check the service's current domain
  count first.

**Cloudflare (DNS for stickballman12.com):**
- Add `CNAME  supplier → <target>.up.railway.app`.
- Set **DNS-only (grey cloud)** first so Railway can verify + issue the cert, then optionally
  **Proxied (orange)**. If proxied, SSL/TLS mode must be **Full (strict)** — *Flexible causes
  a redirect loop with Railway.* Match whatever the apex already uses.
- For a low-traffic internal portal, **DNS-only is the least-friction choice** (skips the cert
  dance); proxy only if you want Cloudflare WAF/DDoS on that host.

**App gating (Phase 1, not infra):** if `location.hostname` starts with `supplier.`, render the
supplier-only shell (login → scan-out home) and hide staff/PH surfaces. **Never trust the
hostname for authz** — every PO endpoint scopes the `supplier` user to their own POs. DNS can
be provisioned any time; until the gating ships, the subdomain just shows the normal app.
